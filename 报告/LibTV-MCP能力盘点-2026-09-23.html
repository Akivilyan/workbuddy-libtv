1. MCP 通道确认可用，且已端到端跑通。完整走完「动态客户端注册 → OAuth 2.1 + PKCE 授权 → 换 token → initialize → tools/list → 实际调用」全链路，每一步都拿到 200 / 201。不是"看起来能用"，是真的调通并读回了真实数据。
2. 能力面明显大于 CLI —— 你之前的判断是对的。CLI 覆盖的是"建节点 + 触发 + 上传下载"这条主干；MCP 在这之上多出五大块：成片合成导出、媒体语义理解、Script V2 表与时间线编辑、生成前零成本预检、远端 Agent 委托。
3. 技术上可以接进 WorkBuddy，但有一处需要你拍板。MCP 不依赖本地 CLI（localRuntimeRequired: false），token 可自动续期。代价是授权范围包含 project:write / media:write / task:write / export:write —— 接进来之后，调用生成接口就是花积分，护栏得靠流程（先报方案）而不是靠权限。

五、关键发现与坑

validate_generation_plan 是这次最有价值的发现。它零成本、不改画布（persisted: false），却把云端最终要发的请求体完整吐出来 —— 包括 imageList（每张图的 url 与像素尺寸）、imageListOrder 与 mixedListOrder、advancedSettings.extendPrompt、以及模型解析结果（requestedMode → modeType）。
实测示例（A 组画布，Wan 3.0 / mixed2video / 15s / 720P / 2 张参考图）返回 valid: true, status: ready，并把引用名精确解析成 nodeId。
对我们的流程意味着：「生成前必须报方案」这条铁律，从"我口述参数"升级为"零成本跑一次预检，把客观请求体摆给你看"。方案对不对、图挂没挂上、参数有没有被默认值覆盖，全部在花积分之前可见。
坑 1：参数命名不统一，两套风格混用。同一份工具清单里，target_project 要 projectId、generate_video 要 idempotencyKey（camelCase），而 export_video、generation_submit 要 project_id、idempotency_key（snake_case）。凭直觉传参必错 —— 一定要先读该工具自己的 inputSchema。我第一次就踩了（用 project_id 调 target_project，报 pydantic missing 错误）。
坑 2：enableSound 在 MCP 里是字符串 "on"/"off"，不是布尔。预检直接报错 "params.settings.enableSound=false 不在允许范围。可选: on, off"。CLI 侧我们用的也是字符串，一致；但如果按 JSON 直觉传 false 会被拒。
坑 3：access_token 只有 1 小时，refresh_token 会旋转。每次刷新都会换发新的 refresh_token，必须落盘最新的那个，旧的立刻失效。好消息是续期链路已验证可用（200），所以接入后不需要你反复点授权。
其他值得记的细节：
  • Wan 3.0 的 schema 里带着 supportAttachment —— 支持 docx/xlsx/pptx/pdf/txt/md 等文档（上限 1 个、100MB）与网页链接输入。这与模型描述"支持文档与网页输入"对应，是 CLI 侧没利用过的输入通道。
  • MCP 读回的 editorUrl 形如 www.liblib.tv/canvas?projectId=…&launchSurface=codex，并附带一套浏览器交接策略（复用标签页、失败则回退为返回链接）。这是把"点开画布看一眼"也纳入了工具链。
  • read_project 的 mediaPersistence 明确声明："存在绑定 ≠ 媒体可用或可播放"，不做过强断言 —— 服务端在这点上比预期严谨。
  • 服务端九模块全部标着 parityVerified: false，即官方未承诺 MCP 与本地插件能力完全对齐。

六、建议下一步

  • 建议接入，但按"只读先行"的节奏。先把 MCP 写进 ~/.workbuddy/mcp.json，授权后先用 doctor / read_project / validate_generation_plan 三个只读工具替换掉现在靠 CLI 猜测的部分 —— 零积分成本，立刻见效。生成类工具（generate_video）暂时不上，等预检跑顺了再说。
  • CLI 不必退役。两条通道读同一份画布数据（已交叉验证），CLI 在批量操作和脚本可控性上更顺手；MCP 补的是导出、理解、时间线、预检这些 CLI 根本没有的环节。并存没有冲突。
  • 真正该重新评估的是"终剪"这一段。我们现在用本地 ffmpeg 合帧做终剪，而 MCP 提供了 read_timeline / apply_timeline_edit / export_video 一整套云端时间线与导出。要不要把终剪搬到云端，取决于导出质量与积分成本是否可接受 —— 这需要跑一次真实导出才知道，属于要花积分才能验证的项目。是否验证，请你定。
  • 这次探测用的临时 OAuth 客户端（libtv-mcp-probe）与 token 存放在工作区 .tmp\mcp_probe\。接正式通道时建议重新注册一个专用客户端，别复用探测用的这一个。
