二、查出的最大衔接缺漏 高危

旧的版本发现渠道已经"假最新"了 —— 照它走会把 CLI 降级回去。

https://liblibai-web-static.liblib.cloud/cli/latest/manifest.json 现在仍返回 {"version":"1.0.2"}， 但实际最新已经是 1.1.3。它已停止同步。

危险点在于：本机的官方安装脚本正是按这个文件取版本号的 —— 也就是说，谁再跑一次旧安装脚本， 会安静地把 1.1.3 降级回 1.0.2，而且不会报任何错。

官方 1.1.3 的 scripts/install.md 已改口：版本号、安装脚本 URL、skill 包 URL 统一由活动接口下发， 并明确要求"不要再按 …/cli/<version>/… 自行拼接"。
顺带暴露一个方法论问题，值得单独记下来。
我们那份接入规程里写过一条"版本双来源互证"：本地 --version = 1.0.2，官方 manifest.json = 1.0.2， "两个独立来源一致，才敢说装的是最新版"。
当时对，现在错。这两个来源其实同源于同一份未更新的 CDN 文件 —— 一致性只是"同错"。 跨来源互证要挑发布链路不同的来源（本地二进制自报 / 活动配置接口 / 文件更新时间戳）， 不能是同一 CDN 下的两个文件。这条已写回规程文档。

唯一权威的版本发现接口

https://api2.liblib.art/api/www/landing-activities/getById?id=240

响应 data.linkUrl 是一段 JSON 字符串： { version, install:{CMD,PowerShell,shell}, skill }。 实测返回 version = 1.1.3。二进制分包地址：…/cli/<version>/libtv-windows-amd64.zip。

五、结论

1. 你担心的"衔接缺漏"确实存在，而且找到了一处高危险的。 不是 CLI 命令不兼容 —— 恰恰相反，我们实际用到的命令（node create -t、--left、-s、model search、project use、upload、download）参数全部没变。 危险的是版本发现链路：旧的 manifest.json 会给假最新，且旧安装脚本会据此降级。
2. 我们原先标着【待实测】的素材指代问题，其实一直有官方答案。 {{Node …}} 就在官方命令手册里，我们此前没拿到那份手册（当时只装了第三方知识包）。 这次升级顺带把官方 skill 包拿到了 —— 这类"文档缺口导致的重复摸索"才是真正要防的衔接风险。
